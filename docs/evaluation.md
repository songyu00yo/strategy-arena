# 评测规范与运行

修复裁决规则后，可以用 `node --import tsx scripts/audit-verdict-records.ts <历史运行目录> <新审计文件.json>` 对保留的原始结构化裁决做离线核对。它只比较旧规则结果与当前规则结果，不发模型请求、不改旧记录，也不产生新的完整轨迹或质量评分。初始裁决变化可能影响后续模型上下文，离线核对不能模拟这种影响。

## 当前状态与数据边界

状态：**修复前的冻结留出调用已结束，人工质量评分尚未完成**。运行器和记录工具已经实现。自动化测试使用明确标注的模型适配器替身，单元测试成功不代表真实模型效果。真实运行以对应目录的 `metadata.json`、原始记录和人工标签为准。

[协议定义](../evals/protocol.json) 固定三组、步骤和预算，并随运行记录保存哈希。[案例定义](../evals/cases.json) 包含 4 个开发案例和 8 个留出案例。留出案例在学习、生活、工作和创作中各有 2 个。每个案例包含初始条件、变化条件、应当调整的事项和不得引入的错误。

仓库中的留出案例可以被开发者读取，因此不能称为真正的封存盲测。正式评测前冻结案例文件的 SHA-256，并交给独立保管人。若继续使用公开案例，应称为冻结留出评测。结果匿名评分和输入封存是两件事，随机标签不能让公开输入变成盲测输入。

4 个开发案例可以用于调试提示词。冻结留出案例后，不根据留出成绩修改提示词，再把同一组重跑成绩当作最终结果。任何改动都需要新的评测版本和原因记录。

## 三组对照

| 组名            | 信息与流程                                                                                |
| --------------- | ----------------------------------------------------------------------------------------- |
| `strong-single` | 同一个助手顺序提出 3 个候选，读取本组前面的完整输出，再检查和修订。质疑可以考虑全部候选。 |
| `independent`   | 3 个角色独立提案，各自只检查自己的策略、质疑和工具证据。最终裁决读取 3 个修订结果。       |
| `arena`         | 3 个角色独立提案，交叉质疑其他策略，读取本组工具证据后修订，再裁决。                      |

每种条件固定安排 3 次提案、3 次质疑、工具核验、3 次修订和 1 次裁决。完成两种条件需要 20 次常规模型调用。每个步骤遇到已知格式或引用错误时，最多增加 1 次显式修复。原始失败与用量保留，修复也计入费用和 Token。

当前协议为 `2.1.0`。3 组使用同一 DeepSeek 配置、温度、单次输出上限、Schema 和确定性工具。本次历史留出运行的配置 `1.2.0` 使用 `deepseek-flash`、`https://api.deepseek.com/beta` 和 `strict-tool`，提示词版本为 `1.1.1`。输出模式由配置明确选择，失败时不自动回退。严格函数 Schema 绑定当前可用的主张、攻击和证据引用，随后仍经过本地 Zod 与关联校验。工具只检索案例给出的材料并计算算术表达式。初始主张编号、引用校验和裁决检查复用运行当时的应用规则。当前候选为配置 `1.2.1`，规则已发生修复，不能把旧工具哈希下的结果视为当前候选质量验证。不会为了填满 3 条路线而补造结果，也不会因方案相似而额外调用模型；相似路线会记录在诊断字段。

变化条件沿用本组初始结果。各角色获得自己的最终策略和变更原因；`strong-single` 还保留本助手此前的输出历史。`independent` 在裁决前不会读取其他角色的提案、质疑、证据或修订。所有组均不读取其他组结果。

## 预算与失败

每条轨迹指同一案例、同一组的“初始条件 + 变化条件”。默认上限如下：

| 范围                          |    上限 |
| ----------------------------- | ------: |
| 每条轨迹费用                  |  1.5 元 |
| 每条轨迹输入与输出 Token 合计 | 600,000 |
| 每条轨迹工具请求              |   12 次 |
| 一次命令总费用                |   20 元 |

同样的上限不代表同样的实际消耗。必须同时报告实际用量、费用、耗时、失败和预留额。每次调用前先预留保守费用与 Token 上界，额度不足时停止发出下一次请求。预算包括格式修复与失败调用，两个条件之间不会重置。

工具次数统计模型请求的材料检索与算术计算。自动比较已给出的预算和时间限制不计入这 12 次请求。每种条件最多 3 条质疑，每条最多 2 个请求，因此两种条件合计最多 12 次。

超时、未收到完整响应或缺少可信用量时，原预留额继续占用，并停止当前轨迹。未知请求不会自动重试。初始条件未完成时，变化条件记录为跳过，仍保留在计划分母中。已知失败后的一次格式修复不能绕过预算。

命令级账本独立于网页服务账本，不会自动合并不同命令的支出。再次运行前，应核对所有运行记录和服务商账单，确保 120 元 API 预算仍保留至少 30 元供评审使用。运行器没有自动恢复功能；中断后必须先检查最后一个 `call_started` 是否已有对应返回记录。

## 运行开发案例与留出案例

先校验定义，再用已有环境配置运行。以下命令读取本机环境文件供 Node.js 使用，不会打印密钥。

```sh
node scripts/validate-evals.mjs
node --env-file=.env.local --import=tsx scripts/run-evals.ts --split development --case dev-learning --max-cny 3 --output artifacts/evaluations
```

`--case` 可以重复，也可以使用逗号分隔。省略时运行分区中的全部案例。其他可选参数为 `--trajectory-cny`、`--max-tokens`、`--max-tools` 和 `--concurrency`。并发数只能设为 1、2 或 3，默认 1。每条轨迹费用最多 1.5 元，一次命令最多 20 元，工具最多 12 次；不能通过参数放宽这些硬限制。

完成开发与小规模试运行后，冻结配置和案例，再运行完整留出分区：

```sh
node --env-file=.env.local --import=tsx scripts/run-evals.ts --split held-out --concurrency 3 --max-cny 17 --output artifacts/evaluations
```

8 个案例 × 3 组，共 24 条轨迹、48 个计划条件输出。失败、跳过和预算耗尽不删除。运行器把案例与组的顺序随机化，实际顺序保存在元数据中。每条轨迹内部仍顺序执行，最多同时推进 3 条轨迹。所有轨迹共享单进程账本，调用前同步预留费用与 Token，再等待网络返回。未完成调用的预留也计入总上限。并发数、实际顺序和预算都保存在元数据中。

输出目录名称包含时间和随机后缀，不覆盖旧运行。目录必须位于已忽略的 `artifacts/` 内。文件默认仅当前用户可读写。进度只打印案例编号、组名、状态和费用，不打印原始输入、模型输出或密钥。

```text
run-<time>-<random>/
  metadata.json
  checkpoint.jsonl
  summary.json
  raw/<trajectory-id>.json
  blind/<random-label>.json
  blind/scorecards.json
  private/blind-mapping.json
```

`checkpoint.jsonl` 在每次请求前和返回后写入并同步到磁盘，保存预留、用量、失败、修复和工具结果。费用与 Token 预留根据实际请求体的保守上界估算，包含当前结构化 Schema 和动态引用，不能只按用户文字长度估算。原始记录包含提交 SHA、工作区是否有未提交变更、提示词和 Schema 版本、配置哈希，以及实际返回的模型标识和响应编号。

`summary.json` 只汇总运行完成情况、费用和预留额，质量分数保持 `null`。模型别名会由服务商更新，不是不可变模型快照。工作区有未提交变更时，记录的提交 SHA 也不能代表完整源码。

## 匿名评分与核对身份

只把 `blind/` 目录交给评分人。`metadata.json`、`raw/` 和 `private/blind-mapping.json` 由保管人保存，评分结束前不交给评分人。每个随机标签对应一条轨迹，初始条件与变化条件在同一张卡中。

匿名卡移除了组名、提示词、调用次数、费用和原始错误详情。生成文本仍可能透露写作风格或推演方式，无法保证完全盲化。保管人应检查显式方法名称是否出现在正文，并记录影响，不能悄悄改写模型答案。

可生成无需安装软件的离线评分页，把它分别交给两位评分人：

```sh
node scripts/build-rating-pack.mjs artifacts/evaluations/实际运行目录 outputs/匿名评分.html
```

双击 HTML，填写评分人代号，逐项阅读初始与变化条件、方案、工具证据和裁决。每项选择 0、1 或 2，填写理由与证据定位，最后点击“导出评分文件”。未评分项保持 `null`。页面只保存当前浏览器的草稿，不联网，也不会替评分人作判断；导出的 JSON 可用于下面的标签核对。仅分享该 HTML 或 `blind/`，不要把私有映射一起交出。匿名评分页保留失败和未完成样本，不能删掉后只评成功记录。

尽可能请两位评分人独立填写 `scorecards.json`。每人使用独立文件。所有分数字段先为 `null`，需要评分人填写 0、1 或 2，并提供 `raterId`、理由和证据定位。失败样本也要评分，不能删掉空白结果后只比较成功样本。

| 指标                   | 2 分依据                                                 | 常见扣分情形                               |
| ---------------------- | -------------------------------------------------------- | ------------------------------------------ |
| `constraintCompliance` | 行动、时间与成本满足明确硬限制。                         | 忽略预算、隐私、身体条件或工具限制。       |
| `claimTraceability`    | 事实有材料依据，估算有假设，未知明确标注。               | 虚构来源、实时价格、用户反馈或精确收益。   |
| `actionability`        | 有具体第一步、检查办法和退出条件。                       | 只有口号，缺少执行对象或验收办法。         |
| `adaptation`           | 初始方案贴合条件；变化后修改受影响内容，并保留有效内容。 | 条件变化后不修改，或引入负向检查中的错误。 |

0 分表示未满足，1 分表示部分满足，2 分表示满足。`positiveChecks` 指出应有的行为，`negativeChecks` 指出应避免的退步。改了多少字、提出多少质疑都不能直接当作质量改进。

人工标签完成后，保管人核对随机标签与真实组名。下面的路径是占位说明，需要替换为实际运行目录和人工文件：

```sh
node scripts/prepare-eval-records.mjs artifacts/evaluations/实际运行目录 private/人工评分.json private/配对记录.json
node scripts/summarize-evals.mjs --input private/配对记录.json --partition holdout --output artifacts/evaluation-summary.json
```

准备工具拒绝空白分数、重复标签、缺失样本和混用评分人。它从真实轨迹提取用量，保留未知预留与跳过状态，不生成质量评分。两位评分人的标签分别汇总，再记录分歧与复核依据。

完整留出汇总需要 48 条带人工评分的记录，完整开发分区需要 24 条。只选单个开发案例的小规模运行可以用于调试和查看卡片，不能冒充完整分区结果。

汇总器检查同一模型与工具配置、配对完整性和两个条件共享的预算，计算证据文件哈希，并输出描述性均值与逐案差值。公开汇总只保留评分理由的哈希，原始理由留在私有文件中。公开前仍需检查证据路径和其他元数据。

8 个留出案例不足以支持广泛优越性或统计显著性结论。结果需要报告失败、差值分布和限制。禁止把同一 DeepSeek 模型的 3 组比较写成“战胜 GPT”。
