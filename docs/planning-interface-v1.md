# 分析工作台接口约定

## 范围与数据归属

共享合同为 `2.0.0`，见 `src/lib/planning-contracts.ts`。状态机位于 `src/lib/server/planning.ts`。产品只交付可行性分析和制作指引，`productScope` 固定为 `analysis_and_guidance`。

`PlanningSnapshot` 是服务端状态，包含当前会话和有序事件。浏览器只保存输入草稿、纸窗状态、动画队列和待核对请求，不能制造 Agent 输出、保存事件或分析进度。

`revision` 表示项目内容版本。`snapshotVersion` 随每次可见状态变化递增，包括公开输出片段。前端拒绝其他会话或旧版本快照；相同版本不重复更新工作台。`eventCursor` 只用于事件去重。

来源以 kind 和 id 关联 `sourceRecords`。用户原话、材料和模型分析保持不同来源身份。引用模型分析不意味着该内容已经核实。

## API

| 请求                              | 输入                  | 成功响应                     |
| --------------------------------- | --------------------- | ---------------------------- |
| `POST /api/planning`              | `CreatePlanningInput` | `PlanningSnapshot`，HTTP 201 |
| `GET /api/planning/{id}`          | 无                    | `PlanningSnapshot`，HTTP 200 |
| `POST /api/planning/{id}/actions` | `PlanningAction`      | `PlanningSnapshot`，HTTP 200 |

创建只保存会话，不请求模型。后端沿用 owner Cookie、同源检查、模型选择和计费适配器。缺少模型配置时返回实际错误，不使用替身响应。

所有变更带唯一 `operationId`。重试同一操作时保留 ID 与参数，不同参数复用同一 ID 应拒绝。请求结果未知时先核对原请求，不能换 ID 盲目重发。除创建外，动作携带用户所见的 `revision`。

## 动作

| kind          | 含义                                             |
| ------------- | ------------------------------------------------ |
| `advance`     | 执行下一项真实工作，一次动作不包含无限循环       |
| `answer`      | 保存当前问题版本的实际答案                       |
| `note`        | 保存补充或纠正，必要时使受影响分析失效           |
| `preview`     | 提前结束本轮问答，进入可行性与制作路径分析       |
| `confirm`     | 采用指定 reportId 和 fingerprint 的当前分析      |
| `start_round` | 用户显式开启最多 3 题的补充轮次                  |
| `stop`        | 停止后续推进，已发出的模型请求继续记录结果与用量 |

能力字段由服务端计算。浏览器根据最新 `canAdvance` 和 `nextAction=advance` 自动推进；工作中不创建第二条调度循环。最终报告形成后停止自动推进，`start_round` 不能由自动效果触发。

## 问答边界与进度

`progress` 包含当前轮次、本轮问题额度、已发出、已回答、未答额度、尚可发问数量、当前有效问题数、当前阶段、额度耗尽和提前结束标记。

首轮最多 8 题，补充轮次最多 3 题。服务端按实际发出的题目扣除额度。未知、跳过和撤题不退回发问额度。模型返回超出剩余额度的问题不能越过服务端边界。

阶段为理解、关键取舍、可行性、制作路径、综合分析和报告。到达提问边界或用户提前生成后，自动完成收尾与 D、E、C 工作；每个角色仍是独立、受计费和操作锁保护的调用。

覆盖检查包括目标、资源、时间与成本、限制、风险、制作路径和最小可行版本。每项保留说明、相关事项与评估角色。它表示实际分析状态，不是倒计时或主观完成百分比。

旧会话读取时补齐新字段及 D、E 的空闲状态，不伪造其运行记录。已发出的历史问题不应因升级重新获得无限额度。

## Agent 公开内容

五角色顺序为 A、B、D、E、C。A 理解需求，B 提出关键取舍，D 判断可行性，E 整理制作路径，C 综合报告。

卡片读取真实 `status`、`taskLabel`、`summary` 和 `preview`，并关联事件和事项。`preview` 只包含面向用户的可读输出，不能展示模型内部推理或提示词。最终成果通过校验后才进入正式内容。

D、E 的 `expertResults` 保存真实模型结论、公开章节、风险、未知、建议下一步和最小可行版本。结论可以是可行、有条件可行、不可行或信息不足；不要求每个项目都得出可行。

## 问题与保存

问题的 `askedBy` 与 `answerTo` 决定纸张的来源和落点。单选的明确点击或确认按键触发保存；箭头切换焦点不触发。多选、文字和数字通过继续动作提交。

提交携带 `questionId + questionVersion`。选项、文字和数字分别传入对应字段。未知和跳过保持原意，不能写成用户确认。

只有匹配当前操作的 `answer_saved` 才显示成功回执。若 POST 响应中断，GET 已经证明同一个操作保存成功，客户端按成功完成并释放操作锁，不重复提交。失败保留草稿，未知请求保留原操作身份。

## 报告与采用

报告提供项目理解、可行性、制作路径、风险和未决事项。用户界面及复制、下载不展示内部 `executionPrompt`，也不输出请求标识、内容指纹或调试字段。用户导出根据面向用户的结构化内容生成。

`confirm` 只表示用户采用当前分析报告，不把 AI 建议、未知或跳过事项批量提升为用户确认事实。完整披露条件的不可行报告，也可以是有效交付。

采用仍要求当前报告和查漏对应当前内容版本，核对 reportId、内容指纹和报告指纹。当前分析不完整、存在尚未处理的分析阻塞或报告过期时，不能采用。确认时间等元数据不改变正文指纹。

服务端将未决要求和未知条件保留在报告中。界面不以减少提示为由删去会影响可行性的未知。

## 事件与动效

事件保留稳定 id、seq、from、to 以及关联的问题、答案和事项。内部标识服务于程序，不直接显示给用户。

同一事件只播放一次。首次恢复把已有事件作为历史，不重新投递旧问题。用户仍可手动打开当前问题。动画结束只能改变显示状态，不能提交答案、调用模型或确认报告。

纸窗打开时不冻结后台公开工作状态。动画处理结束姿态、取消、连续问答、视口变化及减少动效偏好。高信息密度视图避免相同快照重复渲染。

## 实现与验证

生产代码、测试替身、真实模型运行和部署分别记录。新单元测试检查硬性问题上限、续轮、旧会话兼容、报告来源、未知保留和确认语义。浏览器测试检查自动单选、连续问答、失败恢复、五面板、用户导出和窄屏。

旧路线流程保留 `/?legacy=1` 和既有 `?arena` 入口。原有依赖、锁文件和计费规则继续复用。
