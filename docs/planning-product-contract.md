# 方案擂台产品与交互要求

## 已确认的目的

用户可以只提出一个模糊想法。多个 Agent 帮助用户发现问题、构思可能性、理解取舍，并根据用户的选择和纠正持续细化。最终交付经用户确认的执行方案，可以交给人或 AI 落实。

用户不需要预先写完整需求。系统应给出具体、可比较的选择，承担分析和构思工作。用户可以选择、填写、追问、否定、补充，或者暂时不知道。回答必须改变后续问题和方案。

功能、内容、流程和风格是检查遗漏的方面，不是固定问卷。多个 Agent 的讨论应影响实际方案。完成不取决于提问轮数或动画播放完毕。

## 当前视觉基线

沿用上传的 Opus 原版。保留纸张、墨迹、印章、三卡构图、排版、色彩、空间层次和已有动效的质感。原版已有抽纸、四角投影、回收、翻页、落点反馈及独立叙事时钟。

新增交互应延续这些设计。不要改成聊天气泡、通用管理面板或另一套主题。不要通过删除动效、压缩全部时长来达到快速进入的要求。

## 进入与工作台

首页输入原始想法后，立即开始进入工作台的界面过渡。创建任务只创建真实状态，不调用模型。创建成功后显示三张 Agent 卡片，再发起分析。

首次模型结果返回前，三卡工作台已经可见。暂时没有内容的卡片显示真实的待开始或处理中状态。创建失败时保留用户原始输入，并提供恢复路径。

理解需求、提问、用户作答、讨论、查漏、方案预览和最终确认，都在这个工作台内完成。不要在首页设置必须答完的补问关卡。

## 问题纸窗

问题在靠右的纸窗中展开。桌面上应保持多 Agent 工作台的空间关系。窄屏可以使用适合阅读的抽屉布局，同时保留来源角色的标识。

每个问题显示具体内容、必要的提问理由和可比较选项。支持单选、多选、文字、数字，以及服务器允许的暂时不知道和跳过。用户可补充自己的想法。默认不替用户选答案。

用户提交后立即得到本地操作反馈。只有服务器保存成功，才能表现为已收到答案。保存失败时保留输入，纸窗不能无条件关闭或显示成功印章。

回答保存成功后，从实际发起角色递出的纸张形成回执，回到实际接收角色。回执展示用户真实回答。动画结束只改变显示状态，不能提交答案或伪造下一轮任务。

## 动效要求

“快”用于进入工作台和响应用户操作。展开、递交、翻页、回收和归档保持从容、细腻的节奏。

纸张运动要有实际来源、目标落点、轨迹、厚度、阴影和层次变化。角色发出问题、用户阅读、回答回传、讨论更新、方案归档，需要各自清楚的动作。具体时长和曲线根据原版调整，不把未经目视验证的固定毫秒数当作完成标准。

复用 `StepCard.tsx` 的抽纸与四角投影，`RouteStage.tsx` 的三卡运动，以及 `motion-runtime.ts` 的暂停和生命周期。阅读纸窗时暂停背景叙事，交互动画继续响应。暂停叙事不表示服务端任务已停止。

同一事件只在首次收到时播放一次。刷新、重连、轮询、查看历史和组件重新挂载都不能重复投递。过期事件与当前题目不一致时，不重新弹出旧问题。用户打开当前问题的按钮始终可用。

处理快速开关、连续点击、动画中断、尺寸改变、页面切换和减少动效偏好。清理临时 DOM、定时器与动画句柄，恢复焦点。华丽动效不能阻断填写或让文字长时间不可读。

## 最终执行方案

报告至少说明目标、适用范围、已确认要求、功能与内容、使用流程、风格、实施路径、任务依赖、风险、未决事项、验收方法和执行提示词。

用户决定、AI 建议、材料事实和未知项分别标明。报告能追溯到相关回答或材料。用户可以先查看阶段草稿；查看草稿不能把未答题标成已答，也不能冒充正式确认。

正式交付绑定当前内容版本、当前查漏结果和当前报告。用户修改需求后，旧报告保留历史身份，不能继续作为已确认的当前方案。

## 第一条真实验收案例

使用用户这次项目改造作为首个真实案例：保留原版视觉，尽快进入多 Agent 工作台，在工作台里帮助表达不完整的人逐步形成执行方案。

记录实际输入、每轮问题与选项、用户亲自回答、回答对后续内容的影响，以及最终执行方案。测试替身只能证明交互行为。真实模型输出与真实用户确认需要分别记录。

## 前端验收

1. 提交原始想法后，首次分析完成前就能看到原有风格的三卡工作台。
2. 工作台中出现右侧问题纸窗；用户选择后，下一轮使用这个真实答案。
3. 改选、否定或补充会改变后续展示；没有固定两轮收尾。
4. 递纸和回执有实际来源、实际去向及稳定事件标识。
5. 保存失败保留输入；重连不自动重发未知请求，也不重播旧问题。
6. 阶段草稿、查漏通过和用户正式确认具有不同含义与表现。
7. 旧记录仍能阅读和回放。新业务不伪装成旧路线提案或裁决。
8. 桌面与窄屏可用；动效中断、键盘操作和减少动效均可正常完成任务。

## 实施责任

用户已决定由当前开发方统一推进前端、后端、动效、测试与集成。此前为外部 GPT 6.1 准备的分工不再作为实施前提。

共享类型、服务端状态与界面行为以同一套接口为准。内部并行开发按文件分工，由主开发统一审阅和验证，不要求用户在不同开发对话之间传递状态。
