# 评测规范

## 当前状态与数据边界

状态：**NOT RUN，尚未完成模型对照评测**。[案例定义](../evals/cases.json) 包含 4 个开发案例和 8 个留出案例。留出案例在学习、生活、工作和创作中各有 2 个。每个案例包含初始条件、变化条件、应当调整的事项和不得引入的错误。

仓库中的留出案例可以被开发者读取，因此当前不能称为真正的封存盲测。正式评测前先冻结案例文件的 SHA-256，再交给独立保管人。保管人应另存未向开发者公开的输入；开发者只在评分结束后拿到结果。若仍使用公开案例，应如实称为冻结留出评测。

4 个开发案例可以用于调试提示词。冻结留出案例后，不根据留出结果修改提示词并重跑同一组作为最终成绩。任何改动都要创建新的评测版本，并记录原因。

## 三组对照

| 组名 | 流程 |
| --- | --- |
| `single` | 直接为目标生成一个方案与条件判断。 |
| `reflection` | 先生成方案，再自查关键前提、核验并修订。 |
| `arena` | 3 条独立策略相互质疑，核验后修订并裁决。 |

同一案例与条件下，3 组使用相同模型配置、工具权限和总预算上限。保留总输入与输出 Token、工具次数、人民币估算和耗时。预算必须覆盖组内全部调用，不能只统计最后一次回答。格式修复、失败调用和重试也要计入预算与耗时。各组可以提前完成，不能为用满预算而增加无意义调用。

初始条件和变化条件都要运行。运行顺序随机化，并为每组使用独立上下文，避免读取其他组结果。温度、最大输出长度和提示词版本应记录。服务商模型别名不是不可变版本；同时保存响应返回的模型标识、响应编号和运行日期。

正式运行器仍需核对统一预算调度。当前交付定义校验与记录汇总工具，不把手工记录工具称为已执行的公平对照实验。

## 评分与防回归

每个指标采用 0、1、2 分：0 表示未满足，1 表示部分满足，2 表示满足。评分理由必须引用输出或工具证据。尽可能由两位不了解组名的评分人独立评分，再记录分歧与复核结果。

| 指标 | 2 分依据 | 常见扣分情形 |
| --- | --- | --- |
| `constraintCompliance` | 行动、时间与成本均满足明确硬限制。 | 忽略预算、隐私、身体条件或工具限制。 |
| `claimTraceability` | 事实有材料依据，估算有假设，未知明确标注。 | 虚构来源、实时价格、用户反馈或精确收益。 |
| `actionability` | 有具体第一步、检查办法和退出条件。 | 只有口号，步骤缺少执行对象或验收办法。 |
| `adaptation` | 初始条件下方案与条件一致；变化后改动受影响内容，并保留仍然有效的内容。 | 条件变化后不修改，或引入案例负向检查中的错误。 |

`positiveChecks` 指出应有的行为，`negativeChecks` 指出应避免的退步。不能把“改了多少字”或“提出了多少质疑”当作改进程度。缺信息时保留未知，可能比强行给出建议得分更高。

失败、预算耗尽和超时必须保留，不能仅汇总成功样本。初始条件下的 `adaptation` 检查方案是否贴合给定条件；变化条件下检查是否合理调整。

## 记录与汇总

先校验案例定义：

```sh
node scripts/validate-evals.mjs
```

实际运行后，在私有目录保存记录 JSON。每个案例、每种条件需要 3 条记录，组名分别为 `single`、`reflection` 和 `arena`。每份文件只包含一次重复和一个分区。结构见下方，内容是字段说明，不是测试结果。

```json
{
  "records": [
    {
      "caseId": "hold-learning-1",
      "condition": "initial",
      "arm": "single",
      "model": "deepseek-flash",
      "modelConfigHash": "实际配置文件的 SHA-256",
      "toolPolicyHash": "实际工具权限定义的 SHA-256",
      "promptVersion": "实际提示词版本",
      "budget": { "maxTokens": 24000, "maxToolCalls": 12, "maxCny": 1.5 },
      "usage": { "inputTokens": 0, "outputTokens": 0, "toolCalls": 0, "costCny": 0 },
      "durationMs": 0,
      "status": "failed",
      "scores": { "constraintCompliance": 0, "claimTraceability": 0, "actionability": 0, "adaptation": 0 },
      "scoreReason": "填写真实评分理由和证据定位。",
      "artifactPath": "private/evaluation/实际运行证据.json"
    }
  ]
}
```

上面的单条字段示例不能单独通过汇总。完整留出文件应有 48 条真实记录：8 个案例 × 2 种条件 × 3 组。开发分区应有 24 条。预算数值需要在运行前登记，示例数值不代表实际授权。

```sh
node scripts/summarize-evals.mjs --input private/evaluation/records.json --partition holdout --output artifacts/evaluation-summary.json
```

汇总器校验配对完整性、相同模型与预算、用量上限和评分范围，并计算证据文件哈希。输出只给出描述性平均值、费用、耗时和逐案差值。它不能核实人工输入的真实性，也不调用模型。汇总文件只保存评分理由的哈希；原始理由留在私有记录中。公开前仍需检查证据路径，避免暴露私人信息。

8 个留出案例不足以支持广泛优越性或统计显著性结论。结果需要同时报告失败案例、差值分布和限制。禁止将同一 DeepSeek 模型的 3 组比较写成“战胜 GPT”。
